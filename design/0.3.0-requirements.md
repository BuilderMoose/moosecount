# moosecount 0.3.0 — Language-Aware Counting

## Why

One C-family state machine is applied to all sixteen default extensions. It is
wrong for several of them, silently. A Rust file containing `&'static str`
opens a string that never closes and swallows the rest of the file:

```rust
fn main() {
    let s: &'static str = "hello";
    println!("{}", s);
}

// this comment should be counted as a comment
/* and so should this one */
```

Reported as 6 code lines, 0 comments, 0 format lines. Anything reached with
`--ext` is worse — `--ext py` counts `# comment` as code.

0.3.0 replaces the parser with a table-driven design: one state machine, driven
by a per-language specification. That is the whole theme of the release.

## Goals

- Counting is correct for every language in the default set.
- Adding a language is data, not code.
- The parser is unit-testable without running the binary.

## Non-goals for this release

- JSON output. The output model is changing here; freezing a schema around a
  data model still being discovered is a mistake. It follows in 0.4.0.
- Parallel traversal. Premature until the parser settles.
- Coverage reporting. Added after the tests exist, as its own change.
- Any change to ignore-rule behavior. That work is finished and stays as-is.

## Counting specification

This exists today only as the behavior of `processFile()`. Per-language parsers
all have to agree on what they produce, so it is written down first.

Every line is classified by what it contains, after the language's comment and
string rules have been applied:

| Category | Definition |
| --- | --- |
| **Blank** | No non-whitespace characters. |
| **Comment** | Contains at least one character of comment content. |
| **Format** | Contains only the language's structural delimiters, and no code or comment. |
| **Code** | Contains anything else. |

A line may be both code and comment. Format is exclusive by construction: a
line with any code or comment on it is not a format line. `Total` counts every
line; `Lines of Code` stays `code + format`.

Structural delimiters become a per-language property (`formatChars`), `{` and
`}` for the C family. **Python therefore reports zero format lines, and that is
correct rather than a degradation** — Python expresses structure with
indentation, which occupies no lines of its own. Any language without
brace-only lines should report zero.

## Language specification model

```
LanguageSpec
  name                "C++", "Python", "Rust"
  extensions          .cpp .cc .hpp ...
  lineComments        "//"           (a list; some languages have several)
  blockComments       ("/*", "*/")   (a list of pairs)
  blockCommentsNest   false          (true for Rust, Swift, D)
  stringDelimiters    " '  `        (each with its own escape rule)
  formatChars         { }
  quirks              flags, see below
```

Worked examples:

- **C++** — line `//`, block `/* */` non-nesting, strings `"` and `'` with
  backslash escapes, format `{}`.
- **Python** — line `#`, no block comments, strings `"` `'` `"""` `'''`,
  no format chars.
- **Rust** — line `//`, block `/* */` **nesting**, strings `"` and raw `r#"`,
  char literals that must not be confused with lifetimes, format `{}`.

### Quirks

Some languages cannot be expressed as a table. Each gets an explicit flag so
the limitation is visible in the data rather than buried in the parser:

- `lifetimeApostrophe` (Rust) — `'` opens a char literal only when it closes
  within a few characters; otherwise it is a lifetime. This is the fix for the
  bug that motivated the release.
- `rawStringPrefix` (Rust, C++) — `r#"..."#`, `R"(...)"`.
- `tripleQuotes` (Python) — multi-character string delimiters.

### Accepted limitations

Documented, not fixed:

- **JavaScript regex literals.** Telling `/` as division from `/` as a regex
  requires real parsing. A regex containing a quote will desynchronize the
  string state.
- **Shell heredocs.**

Both belong in the README's limitations section so a wrong count is
explainable rather than mysterious.

## Decisions to confirm

**D1. Python docstrings — comment or code?** Recommend **code**. A state
machine cannot reliably distinguish a docstring from any other triple-quoted
string, and the heuristic version ("first statement in a file or function")
needs structure the parser does not have. cloc calls them comments; we would
differ, and should say so in the README.

**D2. Unknown extensions.** Recommend a **generic spec** — blank versus
non-blank, no comment detection — plus a one-time warning naming the
extension. Falling back to the C-family spec is what produces today's silent
miscounting.

**D3. Default extension set.** Recommend **every language with a real spec is
in the defaults**. Simple rule, easy to explain. Consequence: `.py`, `.sh` and
similar begin being counted in trees where they were previously skipped.

**D4. Output grouping.** Recommend replacing the `By Extension` block with
**`By Language`**, so `.cc`, `.cpp` and `.hpp` aggregate under C++. This is the
point of the release, and the current block is the only place extensions
surface in output.

## Compatibility

Numbers will change. Expected and intended:

- Rust files containing lifetimes or nested block comments were wrong; they
  become right.
- Files reached through `--ext` for a language with no spec change from
  "parsed as C" to "counted generically".
- `.py` and similar are counted by default (D3).
- `By Extension` becomes `By Language` (D4).

`--version` moves to 0.3.0. Worth a `CHANGELOG.md` at the same time.

## Architecture

The defect is confined to `processFile()` — about 120 of 716 lines. The ignore
engine, about 295 lines, is correct, well covered, and has no coupling to
parsing. It moves across unchanged; this is a refactor of the parser layer, not
a rewrite of the tool.

```
google/googletest/       git submodule
src/
  counting.hpp           CountTotals, the categories above
  language.hpp/.cpp      LanguageSpec, the registry, extension lookup
  parser.hpp/.cpp        one state machine, driven by a LanguageSpec
  ignore.hpp/.cpp        moved as-is from main.cpp
  walker.hpp/.cpp        traversal, aggregation
main.cpp                 CLI only, links MoosecountLib
tests/
  unit/                  gtest: testerMain.cpp, testParser.cpp, ...
  run_tests.py           existing integration suite, unchanged
  data*/                 existing fixture trees, unchanged
```

Settled: googletest as a submodule under `google/`, matching mooseworks;
gtest tests under `tests/unit/` rather than a second top-level directory one
letter away from `tests/`; `target_link_libraries(tester gtest MoosecountLib)`
by target rather than by path to the `.a`, so build ordering is correct.

Coverage later, behind an explicit `-DENABLE_COVERAGE=ON` rather than wired
into every debug build.

## Testing

The unlock is that a parser test becomes a table of `(snippet → expected
counts)` rather than a fixture tree plus regex-scraped stdout.

- `TEST_P` with a data table per language, so each case is a named failure.
- Every quirk gets a case: Rust lifetimes, nested block comments, raw strings,
  Python triple quotes, a comment inside a string, a string inside a comment.
- The glob matcher and `IgnoreRules` get direct unit tests, which they have
  never had — they are currently only reachable through the binary.
- `tests/run_tests.py` stays as the integration layer: the CLI conventions, the
  ignore fixture trees, end-to-end totals. `make test` runs both.
